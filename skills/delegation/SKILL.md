name: delegation
description: Delegate coding investigations, reviews, and implementation tasks through the Codex subagent extension's MCP server.
---

Call get_current_agent_project to read the current local Git root from original host directory metadata and whether it is registered, then explicitly choose the task repository. If it is unregistered and auto_register_on_task_start is true, starting a task for that repository from this chat registers it (the user's Automatically add chat projects setting, on by default). If host metadata is unavailable, use the actual absolute repository known from the current task context, never a guessed path or `current`. A registered repository grants that Git root only; an approved parent directory permits validated child repositories.

When a read-only check (get_current_agent_project, list_agent_projects, get_agent_panel_context) shows the chat's project is not added and you are not starting a task for it, ask the user whether to add it: call request_agent_project, which shows them a confirmation. Otherwise, if the intended root is missing, call request_agent_project with its known absolute repository, or omit repository to prefill the host root. Wait for accepted registration and use the returned canonical repository before delegating. Honor deny/cancel. If the host cannot show confirmation, direct the user to Add project or Browse in the panel, or the local registration CLI. Never substitute supplied README text and describe it as repository delegation. Explicit paths and host_directory arguments cannot authorize automatic registration; models cannot change the opt-in setting. Registration never starts a task, and disabling opt-in keeps already registered roots.

Use list_available_workers to discover supported providers and limits. Start independent tasks with start_agent_task; use depends_on for ordering and conversation_id for conversation scope. Reviewer, researcher, and security reviewer profiles are read-only. Tasks default to the current repository, including uncommitted changes, with revision="HEAD" and an explicit approved repository. Use workspace_strategy="worktree" for isolated or parallel edits and for an isolated checkout of a committed revision. Review profiles remain read-only; write profiles edit the current checkout directly. Current-repo diffs include pre-existing changes and are not patches attributable solely to the worker.

For a conversational request such as “ask Claude to review my work”, use the actual repository from the current task context, match it to the approved projects, choose the reviewer profile, and pass the full request in description with bounded relevant context to start_agent_task. The service generates a title from the description's first line or sentence, up to 120 characters; an optional title remains an API compatibility override. Browser and native host forms collect only the full description, and task details keep it collapsed until expanded. Its successful result opens Delegated work where the host supports MCP Apps and selects the new task on Activity. Do not create another task just to open its panel. To reopen it, call open_codex_subagent_extension with task_id; to open a prefilled panel before starting, pass repository and revision. Use the thread entrypoint to keep it beside the current chat when available; display placement is controlled by the host.

get_agent_panel_context can resolve defaults from optional host directory metadata or prior work in the same conversation. These are hints validated against registered projects; they never register a project. Explicit repository/task context takes precedence. Do not replace a real directory with a global “last project”, infer a native chat ID from an anonymized correlation ID, or guess undocumented host fields. If several projects remain ambiguous, ask for the missing project. New task prefills known project/revision and worker defaults; users can edit them.

Worktree tasks start from a committed revision and do not copy uncommitted files automatically. To review uncommitted work in a worktree, supply the relevant diff and file excerpts in bounded context or explain which committed revision is being reviewed. Current-repo tasks inspect the live checkout, including uncommitted files. Conversation history is not copied automatically in either workspace strategy.

Tasks are asynchronous. Continue primary work and retrieve state with get_agent_task. Use get_agent_events for execution activity, get_agent_result for structured findings, and get_agent_artifacts for reports and diffs.

Claude tasks default permission_mode to inherit. Resolution uses an explicit task override, then the user's claude_permission_mode setting, then the profile fallback: plan for read-only profiles, and for write profiles the default mode from the user's Claude Code settings (permission_source user_config). Your own permission mode is not passed on. Explicit native Claude modes are default, acceptEdits, plan, dontAsk, auto, and bypassPermissions. The resolved task.permission_mode and permission_source show the actual choice. Keep inherit unless the task needs an authorized override. Under inherit, a model-selected override can only choose plan or dontAsk. Codex native permission settings are outside this change; its existing adapter and turn-level approval flow remain unchanged.

Approval decision routing is separate: approval_decider is user or parent_agent and inherits default_approval_decider (user by default). Native SDK checks can allow or deny an action before it reaches the permission callback. By default a Claude task behaves like the user's Claude Code CLI: all tools including subagents, the user's sandbox settings and environment. The user can enable session restrictions in settings (claude_sandbox, claude_environment, claude_tools, claude_path_guard, claude_subagents); read-only profiles get restricted tools and the path guard unless the user loosens them. Enabled restrictions and repository access checks apply in every native mode. Model-visible update_agent_settings cannot change session restrictions.

A model-selected task override cannot increase permission or approval authority beyond the authorized inherited setting. Trusted panel submissions or user-confirmed host forms can authorize overrides. Model-visible update_agent_settings rejects permission, approval-authority and automatic project registration defaults; user changes use app-only update_user_agent_settings. The panel's host transport uses app-only start_user_agent_task; its standalone console uses authenticated cookie authority.

If a task requires input, use the exact request_id. For questions, submit_agent_input accepts the answer. For permissions with approval_decider=parent_agent, assess the requested action against the user's authorized task scope and approve or deny through submit_agent_input. For user routing, show the pending action to the user and direct them to the panel's Approve/Deny buttons or request_agent_input host form; model-visible submit_agent_input cannot grant that permission. The panel uses app-only submit_user_agent_input. Questions follow native SDK rules; dontAsk can deny them before the callback.

App-only visibility depends on host enforcement; authenticated raw service clients are trusted administrators, and the service does not cryptographically attest human decisions. Legacy Claude approval_mode values migrate to native permissions and routing: ask_user to default/user, parent_agent to default/parent_agent, auto_approve to bypassPermissions, and deny to dontAsk. Persisted legacy tasks and saved host forms retain their legacy permission mode and decision routing when native fields are absent.

Interrupt preserves session state; continue requires its original worker. Steering interrupts the current turn and starts another turn with the instruction. Cancellation retains artifacts. Retry creates a new task.

Inspect returned diffs before applying them. A worktree is code isolation, not an operating-system sandbox. Do not describe interrupted Claude sessions as instruction-pointer pause/resume or promise session portability. Never expose service or provider credentials.
