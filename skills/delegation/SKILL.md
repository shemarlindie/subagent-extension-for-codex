name: delegation
description: Delegate coding investigations, reviews, and implementation tasks through the Codex subagent extension's MCP server.
---

Call get_current_agent_project to read the current local Git root from original host directory metadata and whether it is registered, then explicitly choose the task repository. If it is unregistered and auto_register_on_task_start is true, starting a task for that repository from this chat registers it (the user's Automatically add chat projects setting, on by default). If host metadata is unavailable, use the actual absolute repository known from the current task context, never a guessed path or `current`. A registered repository grants that Git root only; an approved parent directory permits validated child repositories.

When a read-only check (get_current_agent_project, list_agent_projects, get_agent_panel_context) shows the chat's project is not added and you are not starting a task for it, ask the user whether to add it: call request_agent_project, which shows them a confirmation. Otherwise, if the intended root is missing, call request_agent_project with its known absolute repository, or omit repository to prefill the host root. Wait for accepted registration and use the returned canonical repository before delegating. Honor deny/cancel. If the host cannot show confirmation, direct the user to Add project or Browse in the panel, or the local registration CLI. Never substitute supplied README text and describe it as repository delegation. Explicit paths and host_directory arguments cannot authorize automatic registration; models cannot change the opt-in setting. Registration never starts a task, and disabling opt-in keeps already registered roots.

Use list_available_workers to discover supported providers and limits. Start independent tasks with start_agent_task; use depends_on for ordering and conversation_id for conversation scope. Reviewer, researcher, and security reviewer profiles are read-only. Tasks default to the current repository, including uncommitted changes, with revision="HEAD" and an explicit approved repository. Use workspace_strategy="worktree" for isolated or parallel edits and for an isolated checkout of a committed revision. Review profiles remain read-only; write profiles edit the current checkout directly. The diff in a current-repo worker's prompt includes pre-existing changes; get_agent_changes leaves those out but still includes anything else edited in that checkout while the task ran.

For a conversational request such as “ask Claude to review my work”, use the actual repository from the current task context, match it to the approved projects, choose the reviewer profile, and pass the full request in description with bounded relevant context to start_agent_task. The service generates a title from the description's first line or sentence, up to 120 characters. Browser and native host forms collect only the full description, and task details keep it collapsed until expanded. Its successful result opens Delegated Work where the host supports MCP Apps and selects the new task on Chat, where its reply streams in. Do not create another task just to open its panel. To reopen it, call open_codex_subagent_extension with task_id; to open a prefilled panel before starting, pass repository and revision. Use the thread entrypoint to keep it beside the current chat when available; display placement is controlled by the host.

When the user selects the Claude composer mention, treat it as a provider hint only. For a review request such as `@Claude review index.html`, confirm that `list_available_workers` includes Claude and the `reviewer` profile, resolve the repository through the normal approved-project rules, and call `start_agent_task` with `provider: "claude"`, `worker_profile: "reviewer"`, and the full request in `description`. The mention does not identify or authorize a project, attach file contents, or change workspace, permission, or approval settings. If the host does not provide usable project context, ask for the repository rather than guessing.

get_agent_panel_context can resolve defaults from optional host directory metadata or prior work in the same conversation. These are hints validated against registered projects; they never register a project. Explicit repository/task context takes precedence. Do not replace a real directory with a global “last project”, infer a native chat ID from an anonymized correlation ID, or guess undocumented host fields. If several projects remain ambiguous, ask for the missing project. New task prefills known project/revision and worker defaults; users can edit them.

Worktree tasks start from a committed revision and do not copy uncommitted files automatically. To review uncommitted work in a worktree, supply the relevant diff and file excerpts in bounded context or explain which committed revision is being reviewed. Current-repo tasks inspect the live checkout, including uncommitted files. Conversation history is not copied automatically in either workspace strategy.

Tasks are asynchronous conversations. Continue primary work and retrieve state with get_agent_task. Read the conversation with get_agent_messages: it returns the messages after a cursor, including each successful turn's reply (kind reply), the worker's plain account of what it did and what is left. Pass wait_seconds (at most 50) to wait until a message arrives, the turn ends or input is needed, and pass next_cursor back as after. It returns only complete messages. Use get_agent_events for the full execution log. A reply is the worker's own account; read what a turn actually changed with get_agent_changes(scope "turn"). Worktree changes are on the task's branch, `<worktree_branch_prefix><task-id>` (`agent/<task-id>` by default; task.branch names it), in the task's worktree. Use get_agent_changes to read what a task changed: a live Git diff with per-file stats, for the whole task or its latest turn (scope "turn"), paged by file through next_cursor. For current_repo tasks it is measured from a snapshot at task start, so it leaves out earlier uncommitted work but includes later edits anyone made in that checkout.

Claude tasks default permission mode to inherit. Resolution uses an explicit task override, then the user's claude_permission_mode setting, then the profile fallback: plan for read-only profiles, and for write profiles the default mode from the user's Claude Code settings (permission_source user_config). Your own permission mode is not passed on. Explicit native Claude modes are default, acceptEdits, plan, dontAsk, auto, and bypassPermissions. The resolved task.provider_options.claude.permission_mode and permission_source show the actual choice. Keep inherit unless the task needs an authorized override. Under inherit, a model-selected override can only choose plan or dontAsk.

Approval decision routing is separate: provider_options.claude.approval_decider is user or parent_agent and inherits default_approval_decider (user by default). Native SDK checks can allow or deny an action before it reaches the permission callback. By default a Claude task behaves like the user's Claude Code CLI: all tools including subagents, the user's sandbox settings and environment. The user can enable session restrictions in settings (claude_sandbox, claude_environment, claude_tools, claude_path_guard, claude_subagents); read-only profiles get restricted tools and the path guard unless the user loosens them. Enabled restrictions and repository access checks apply in every native mode. Model-visible update_agent_settings cannot change session restrictions.

A model-selected task override cannot increase permission or approval authority beyond the authorized inherited setting. Trusted panel submissions or user-confirmed host forms can authorize overrides. Model-visible update_agent_settings rejects permission, approval-authority and automatic project registration defaults; user changes use app-only update_user_agent_settings. The panel's host transport uses app-only start_user_agent_task; its standalone console uses authenticated cookie authority.

If a task requires input, use the exact request_id. For questions, submit_agent_input accepts the answer. For permissions with provider_options.claude.approval_decider=parent_agent, assess the requested action against the user's authorized task scope and approve or deny through submit_agent_input. For user routing, show the pending action to the user and direct them to the panel's Approve/Deny buttons or request_agent_input host form; model-visible submit_agent_input cannot grant that permission. The panel uses app-only submit_user_agent_input. Questions follow native SDK rules; dontAsk can deny them before the callback.

App-only visibility depends on host enforcement; authenticated raw service clients are trusted administrators, and the service does not cryptographically attest human decisions. New Claude tasks persist native permission state under provider_options.claude; approval_mode is accepted only by providers with whole-execution approval.

A completed task stays open: send_agent_message starts its next turn in the same task, resuming the worker's session (or starting a new session that carries the conversation when it can't resume) and recreating a removed worktree. While a turn runs, delivery chooses how the message arrives: steer (the default) reaches the running turn at its next tool boundary without stopping it, queue waits for a turn of its own after the current one, and interrupt stops the turn and starts the next one with the message and any pending steers. A worker waiting for input can't be steered; answer it with submit_agent_input, or queue the message. Pending steers and queued messages show in get_agent_task; remove_agent_queued_message withdraws a message you queued. interrupt_agent_task stops a turn and keeps the session; its send_pending option sends the pending steers at once as the next turn, and a plain interrupt pauses the queue until the next message is sent. When a turn stops at its budget, send_agent_message's budget raises it (each limit can only go up). Only deleting a task ends it for good.

Inspect returned diffs before applying them. A worktree is code isolation, not an operating-system sandbox. Do not describe interrupted Claude sessions as instruction-pointer pause/resume or promise session portability. Never expose service or provider credentials.
